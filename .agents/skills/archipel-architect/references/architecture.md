# Architecture application

Use with the common Architecture and OOP/design-pattern modules for design, dependency changes, refactoring and migrations. Read the relevant sections of [Archipel conventions](../../../../.github/instructions/archipel-project.instructions.md) and [OOP/design patterns](../../../../.github/instructions/oop-design-patterns.instructions.md).

- Identify the existing capability owner under `libs/platform-*`, the public entry point and its consumers. `tools/` owns generators and the documentation MCP server; `infra/nx-plugins` owns repository executors; `apps/frontend/docs` owns the documentation website.
- Keep the framework generic. Built-in provider adapters belong to their platform library; persistence adapters and application policies supplied by a consumer stay in that application. Do not import FLAMOX365's tenant/billing/event conventions or Mosaik's component system into Archipel.
- Abstract base classes are both the type contract and NestJS DI token. Extend the existing `*Base` under `abstracts/`; never create a competing `*Port`/`ports/` hierarchy. Interfaces belong under `interfaces/` with `I` names. Consumer extension points remain public, explicit and documented.
- Compose modules through their existing `register()`/`registerAsync()`/`forRoot()` contract. Inspect the exact option names and defaults rather than assuming every module accepts the same `client` property or global setting. `libs/platform-payments/src/PaymentModule.ts` demonstrates optional consumer adapters and provider registration; configuration has a separate `forRoot()` bootstrap.
- Preserve downward, acyclic capability dependencies. Compare both runtime imports and published manifests before adding an edge. `platform-core` is not currently dependency-free; use the actual graph rather than historical diagrams as an implementation constraint.
- A public base-class change affects every built-in and consumer-provided adapter. Prefer a compatible extension when it satisfies the task; otherwise describe the changed contract and migration rather than silently adding required abstract members. Release/version decisions remain with the owner.
- Keep the provider-neutral package root independent of optional provider SDKs. Use the library's existing subpath pattern and the [provider packaging checklist](platform.md) when adding, removing or moving a provider.
- Trace relevant bootstrap, persistence, mapping, error, config, health, observability, package-export and documentation consequences before declaring a cross-cutting change complete. Do not turn an ordinary task into a mandatory architecture report.
